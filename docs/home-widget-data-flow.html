How the home-screen widgets get the running task

What the widgets, the floating timer and external launchers show, where that information comes from, and how button presses get back to the app.

Arcane (Missions), branch revive2. Written from reading the code. Not yet measured on a phone.

The short version

  1. The Flutter app works out the task state and writes it into one shared store on the phone: Android's SharedPreferences file named HomeWidgetPreferences.
  2. It then tells Android to redraw the widgets.
  3. Every consumer reads that same store: the widgets, the floating timer bubble, and the day-plan widget.
  4. When a user taps a button on a widget or the bubble, the tap travels back to the app as a small arcane://widget?action=... link.

Nothing talks to the app directly. The store is the only shared memory between them.

1. The app decides the task state

lib/src/services/home_widget_publisher.dart listens to AppProvider. Each change in app state asks for a republish. The publish is debounced by 400 ms and skipped when nothing has changed.

A heartbeat runs every 30 seconds and re-checks the state. Every 5 minutes it forces a full rewrite. The forced rewrite exists so that one missed or failed write cannot leave a stale "running" clock on screen.

Two things publish straight away: a bubble or widget tap (republishNow), and a Widgets Studio preview being pushed (restoreLiveTimerState puts the live timer back afterwards).

2. The state is written to a shared store

lib/src/services/home_widget_service.dart builds a flat map of keys and saves each one with HomeWidget.saveWidgetData. All running-task keys start with arcane.task.

KeyMeaning
hasTaskIs there a task to show at all?
isRunningIs the timer running right now?
title, subtitleTask name and the line under it
sessionStartMsWhen the current running session began (epoch milliseconds). The clock is calculated from this.
accumulatedSecSeconds already logged before this session
pausedAtMsWhen the timer was paused (drives the 10-minute "paused" grace)
isCheckpoint, nextCheckpointThe next checkpoint, for the "check next" button
progressPct, capacityProgress bar and load
dp0..dp4.titleDay-plan entries (the queue)
mt0..mt2.*Multitask entries: title, parent and checkpoints
updatedAtMsAlways written last. Its arrival tells the bubble that everything else is in place.
Why the timestamp is last: the bubble only listens for that key, so it never reads a half-written state.

Other slices use the same pattern with their own prefixes: arcane.fin.* (finance), arcane.bus.* (bus), arcane.goals.* (goals), and arcane.theme for colours.

3. Android is told to redraw

After the values are saved, the service calls HomeWidget.updateWidget with the provider's class name, for example me.ihjas.missions.widgets.RunningTaskWidget. That sends a broadcast. Android calls onUpdate on each widget provider, and the provider re-reads the store and builds the layout it shows.

The providers are declared in AndroidManifest.xml and live in android/app/src/main/kotlin/me/ihjas/missions/widgets/: RunningTaskWidget, DayPlanWidget, FinanceWidget, JournalWidget, BusWidget, GoalsWidget. Shared helpers are in WidgetCommon.kt.

Each provider also has an updatePeriodMillis of 30 minutes (in res/xml/widget_*_info.xml). That is a fallback: if no broadcast arrives, the widget still refreshes at least that often.

How the clock ticks without the app running

RunningTaskWidget.renderRunning does not store a changing number. It reads sessionStartMs and sets an Android Chronometer to that start time. The home screen then counts up by itself. The bubble does the same with its own drawing code.

5. Button taps coming back to the app

A button on a widget or the bubble does not change the app directly. It fires a link:

arcane://widget?action=task_toggle      ENGAGE / HALT
arcane://widget?action=task_check_next  CHECK NEXT
arcane://widget?action=task_finish      FINISH

WidgetActionReceiver.kt handles the link first:

  • It applies a quick "instant feedback" change to the store, so the widget responds at once.
  • If the app is running, it passes the action to Flutter through MainActivity.dispatchWidgetAction.
  • If the app is not running, it starts the app with the link. Flutter reads the link at cold start (HomeWidget.initiallyLaunchedFromHomeWidget).

WidgetActionRouter (lib/src/services/widget_action_router.dart) then maps the action name to the real operation. For example, task_toggle starts or pauses the timer. The change goes through the normal publish, so the widgets and bubble end up showing the same state.

Some buttons open the app instead, such as OPEN PLAN and OPEN TASK. Those use HomeWidgetLaunchIntent.

Timing you can expect

EventTypical delay
Tap ENGAGE on a widgetImmediate visual change from the receiver. App state follows once Flutter handles the action.
Change made inside the appAbout 0.4 s debounce, then the widgets redraw.
Bubble after a task changesAbout 150 ms after updatedAtMs is written.
Widget with nothing changingRefreshes every 30 minutes (provider fallback).
Missed publishCorrected by the 30-second heartbeat, forced every 5 minutes.

These come from the code (debounces, heartbeat and update periods). Real delays depend on the launcher and on Android's battery rules.

Things to know

  • Data is only as fresh as the last write. If the app is killed and no broadcast arrives, widgets show the last saved state. A running clock still counts correctly, because it is calculated from sessionStartMs.
  • Plain SharedPreferences. The values are not encrypted, and they include task titles.
  • Keys are shared by name. Renaming a key in Dart without changing the Kotlin readers silently shows empty values. WidgetCommon.kt, RunningTaskWidget.kt, DayPlanWidget.kt and TaskBubbleOverlay.kt all depend on the arcane.task.* names.
  • Order matters for the bubble. Anything that makes the bubble read the store must write updatedAtMs last.
  • Not measured on a device. The timings are from the code, not from a phone.
