Project facts (confirmed by the owner):
- The `task-dominion` Firebase project hosts only Arcane. No other application shares its RTDB, Firestore or Storage rules, so the "retain other apps' rules" requirement in step 0c does not apply: the repository's rule files are the complete rule set, and no `ARCANE_RULES_REVIEWED` merge is needed.
- The Firebase CLI account in use is the owner's account for this product. Administrator access is therefore available to the release run.
- The off-device backup directory is `backups/` inside this repository (git-ignored, see `.gitignore`). Use `ARCANE_BACKUP_DESTINATION=$PWD/backups` when running the release.
- Android releases are signed with the repository's `debug.keystore`, the same as previous releases, so installed users can upgrade.

Steps 0, 0b, 0c and 3-6 below (sync, Firebase backup and rules, builds, GitHub release, update pointer, verification) are automated by `./build.sh`. It is verbose and logs to `backups/build_<stamp>.log`. Run it on the build machine with `ARCANE_BACKUP_DESTINATION` set; use `--skip-firebase` when administrator access is unavailable, and `--no-push` for a build-only dry run. Steps 1 and 2 (version, release notes) are done by hand before running it.

0. Sync the branch with `git pull --rebase origin <branch>` before starting a release.
0b. Back up Firebase using an authorized administrator account. Use `firebase database:get / --project task-dominion --output backups/firebase_db_<UTC-stamp>.json`, gzip the verified JSON, and copy it to the configured external backup destination. Keep 30 dated backups. Do not use unauthenticated database writes.
0c. Read and preserve the currently deployed RTDB and Firestore rules before deploying the rules in this repository. This Firebase project contains other applications: retain their existing access rules, deny root access, restrict `users/$uid` to its owner, deny client writes to `app_updates` and access to shared provider secrets. Deploy the reviewed rules with `firebase deploy --only database,firestore:rules,storage --project task-dominion`. Verify anonymous root reads and update writes are denied. Administrator access is required; never replace this step with a public write.
1. Set the version name to today's YYYY.M.D and increment the version code using 21YYMMDDxx in pubspec.yaml.
2. Write release notes in latest.md, including any operational steps that are still blocked.
3. Run `scripts/release.sh prepare`. It cleans, analyzes, tests, builds all three split release APKs and the Linux x86_64 bundle, strips the Linux binaries, packages them, copies the changelog, and generates checksummed and Ed25519-signed metadata.
   The private signing key lives at `.release_keys/update_signing.pem`. Keep a private off-device copy. Its public key is compiled into the updater. Never commit or publish the private key. Preserve the existing private Android signing certificate so installed users can upgrade.
4. Commit source and metadata. Push the release tag for that commit first, publish and verify the GitHub assets with `scripts/release.sh publish-github`, then `git push origin HEAD:<branch>`. This keeps the branch's updater metadata from advertising unavailable download URLs. GitHub artifact publication can proceed independently when administrator access to Firebase is blocked; record the blocked administrator steps in the release notes.
5. After steps 0b and 0c succeed, set `ARCANE_BACKUP_DESTINATION` to the off-device backup directory and run `scripts/release.sh publish` to publish signed update metadata through the authenticated Firebase CLI. It verifies an existing GitHub release, or creates and verifies one if needed. The metadata URLs must point to published, downloadable artifacts before the Firebase update pointer is changed.
   APKs, tarballs, private signing keys, and database backups are ignored by Git; do not add them with `git add -f`. The existing Git history is preserved.
   If Firebase publication is blocked, retain the existing Git blobs for the packages its live metadata still references. Remove those compatibility files only after the authenticated Firebase pointer has switched to verified GitHub URLs; new binary artifacts remain excluded from Git.
6. Verify the published package hashes and Firebase metadata. Record the result in docs/data-hazard-implementation.md. Perform the restore drill in that document monthly.

Update pointer findings (2026.10.15 release):
- Firebase RTDB keys cannot contain `.`, `$`, `#`, `[`, `]` or `/`. The checksum and signature maps are keyed by download URL, so they cannot be stored under `/app_updates/latest`. The pointer must omit `package_sha256`, `package_signatures` and `package_sizes`. Do not remove that stripping in `scripts/release.sh`; a write with the maps fails with HTTP 400.
- The app fills in the checksums and signatures itself: when the pointer lacks them, `lib/src/services/update_service.dart` reads `builds/update_info.json` from `raw.githubusercontent.com` on `revive2` and needs its `version_code` to match the pointer. Installation is blocked if no valid SHA-256 is found.
- Before switching the pointer, check that the `revive2` raw copy has the new `version_code` and all three hashes, signatures and sizes. The app also tries the `main` raw copy, which was not updated and did not return JSON; do not rely on it.
- Android-only releases: use `scripts/generate_release_metadata.py --android-only` and `scripts/verify_release_assets.py --android-only`. They omit the Linux bundle and its URLs, which the app treats as optional.
- Storage is not set up on `task-dominion`; the app's cloud backups use Storage, so its rules cannot be deployed until it is enabled in the console.

Release safety check (added after the 2026.10.15 mistake, where the published APKs contained the 2026.10.11 build):
- Before copying or publishing any APK, confirm the version inside it, not just the file name: `aapt dump badging <apk> | grep -m1 "^package:"` must show `versionName='<pubspec version>'` and the expected `versionCode` (the base code, plus 2000 for arm64-v8a, 1000 for armeabi-v7a and 4000 for x86_64).
- Check the source APK's build time against the build run before copying it. Stale files in `build/` look valid.
- `scripts/verify_release_assets.py` checks signatures and hashes, but it does not check the version inside each APK. Run the `aapt` check above in addition.
